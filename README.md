# GitHub Pages LIFF フロントエンド

このフォルダは、Google Apps Script の画面ではなく、GitHub Pages、Vercel、Firebase Hosting などに置く外部 LIFF フロントエンドです。

## 現在の構成

```text
GitHub Pages の index.html
-> LIFF SDK
-> LINE userId 取得
-> JSONP で Apps Script Webアプリ /exec API を呼ぶ
-> Code.gs の doGet(e)
-> saveCheckin(checkinData)
-> Googleスプレッドシートへ appendRow
```

役割は次のように分けています。

- GitHub Pages `index.html`: LINE userId 取得、画面表示、ユーザー操作
- Apps Script `Code.gs`: 入力検証、状態取得、同日重複防止、特典二重使用防止、スプレッドシート保存
- Googleスプレッドシート: 簡易DB、イベントログ

## 現在の完成状態

現在のシステムは、店頭MVPとして一通り動く状態です。

- お客様はLINE LIFF上でチェックインできます
- 本日の2桁店舗コードを入力し、Code.gs側で検証できます
- 再来店特典として「次回ご来店時、対象ドリンク1杯につき100円引き」を表示できます
- 特典対象時は、お客様本人が特典使用ボタンを押せます
- 特典使用は `benefit_used` イベントとして保存されます
- 同日チェックイン重複をサーバー側で防止できます
- 同じ `checkin_id` の特典二重使用をサーバー側で防止できます
- settingsシートに本日の店舗コードと特典有効日数を保存できます
- 従業員グループLINEへ本日のチェックインコードを送信できます
- `setupDailyStoreCodeTrigger()` により、毎日9時台の自動生成トリガーを設定できます
- `APP_MODE = 'customer' / 'dev'` で本番表示と開発表示を切り替えられます
- The TEAのブランドカラーパレットを反映済みです

今後の本番化課題は、不正検知、LINE ID token検証、正式なプライバシーポリシー、問い合わせと削除対応、JSONP以外のAPI方式、スプレッドシートからDBへの移行です。

## なぜ Apps Script 画面をやめたか

Apps Script HtmlService の画面では、実際の実行URLが `script.googleusercontent.com` 側になることがあります。
LIFF では、`liff.init()` を実行するURLが LINE Developers で設定したエンドポイントURLと一致、またはその配下である必要があります。

この条件と Apps Script 画面の実行URLが合わず、`liff.init()` が完了しない問題が出ました。
そのため、画面は GitHub Pages へ移し、Apps Script は保存APIとして使う構成にしています。

この分離により、画面だけを後から作り替えたり、保存APIだけを別バックエンドへ移行したりしやすくなります。

## JSONP を使う理由

GitHub Pages のような外部HTMLから Apps Script を呼ぶ場合、`google.script.run` は使えません。
`google.script.run` は Apps Script HtmlService 内だけで使える仕組みです。

通常の `fetch` POST は CORS で詰まる可能性があります。
MVPでは、まず疎通を優先して JSONP GET 方式を使っています。

JSONP GET で保存する方式は、本格運用向けとしては強くありません。
本番化する場合は、次のような方式を検討します。

- ID token または access token のサーバー側検証
- Cloud Run
- Firebase Functions
- Cloudflare Workers
- Supabase Edge Functions
- Apps Script 以外の通常APIバックエンド

## 再来店特典の有効日数設定

再来店特典の「何日以内」は、`settings` シートの `benefit_valid_days` で調整します。
デフォルトは `7` です。

前回チェックイン日を0日目として、`benefit_valid_days` 日後の終日までが特典対象です。
たとえば `benefit_valid_days = 7` なら、前回チェックイン日 + 7日目の 23:59:59 まで対象です。

これは72時間ぴったりではなく、日付単位の判定です。
店頭で「あと1分早ければ」を避けるため、期限日いっぱいまで対象にしています。

この値は集客の主要調整変数です。
当初は3日前後で検証しましたが、店頭では急かされ感や期限を逃した落胆が出やすかったため、現在の推奨値は7日です。
短くすると短期再来店の圧は強まりますが、落胆や急かされ感が出やすくなります。
長くすると再来店の心理的ハードルは下がり、ログインボーナス的な穏やかさが出ますが、値引き対象は増えます。
売上、特典使用数、通常比販売増を見ながら調整します。

目安は次の通りです。

- 2日〜4日: 短期再来店促進は強いが、急かされ感が出やすい
- 7日: 現時点の推奨。週次来店に近く、落胆を減らしやすい
- 14日: さらに穏やか。値引き対象は増えるが、サービス体験は優しい
- 期限なしに近づける: 来店記録寄りになるが、短期再来店促進は弱まる

管理用関数として、Apps Script側に次の関数があります。

- `setBenefitValidDaysForAdmin(days)`
- `setBenefitValidDaysTo2ForAdmin()`
- `setBenefitValidDaysTo3ForAdmin()`
- `setBenefitValidDaysTo4ForAdmin()`
- `setBenefitValidDaysTo7ForAdmin()`
- `applyRecommendedCheckinSettingsForAdmin()`

GitHub Pages側の `index.html` は日数判定を持ちません。
フロントはサーバーから返る `state.next_checkin_message` と `benefit_status` を表示するだけです。

既に `settings` シートに `benefit_valid_days = 3` が入っている場合、デフォルト値よりsettingsの値が優先されます。
推奨設定へ戻す時は、Apps Scriptエディタから `setBenefitValidDaysTo7ForAdmin()` または `applyRecommendedCheckinSettingsForAdmin()` を手動実行します。

## benefit_status の命名整理

以前は `eligible_72h` / `expired_72h` という状態名を使っていました。
しかし、現在の再来店特典は72時間固定ではなく、`settings.benefit_valid_days` によって7日、14日などへ変更できます。
そのため、時間を含む状態名は現在の運用とズレて見えます。

現在の新規保存では、次の意味ベースの状態名を使います。

- `first_checkin`: 初回または前回履歴がないチェックイン
- `benefit_eligible`: 前回チェックインから有効期間内の再来店。対象ドリンク1杯につき100円引き
- `benefit_period_ended`: 前回分の特典期間が終了した後の来店。本日のチェックインで次回特典を付与
- `benefit_used`: 特典使用済み

既存スプレッドシートには、旧名称 `eligible_72h` / `expired_72h` が残っている場合があります。
これらは過去データとして残して構いません。
過去にどの時点の仕様で保存されたかという履歴でもあるため、一括置換は行いません。

Code.gs と index.html は、読み取り時に旧状態名を新状態名へ正規化して扱います。
つまり、既存の `eligible_72h` 行は画面上では `benefit_eligible` と同じ特典対象として扱われます。
既存の `expired_72h` 行は、画面上では `benefit_period_ended` と同じく「本日のご来店分として次回特典をお付けできます」という文脈で扱われます。

## 店頭運用改善：期限付きクーポンから来店チェックインへ

この施策は、お客様を短期間で急かすための「期限付きクーポン」ではなく、本日のご来店分として次回特典をお付けする「来店チェックイン特典」として運用します。

- 現在の推奨有効日数は7日です
- 3日では急かされ感や期限を過ぎた時の落胆が出やすかったため、週次来店に近い7日へ寄せています
- 期限を過ぎた場合も「失効」ではなく、「本日のチェックインで次回特典をお付けできます」と案内します
- 店舗コードは2桁のまま維持します
- 店舗コードはスタッフの口頭案内だけでなく、店頭POP掲示でも運用できます
- スタッフは全員に強く案内する必要はなく、聞かれた時や余裕がある時に案内する程度で構いません
- 特典使用時だけ、画面に特典対象と表示されているかを丁寧に確認します

店頭POP掲示を使うと、お客様が自分で2桁コードを入力できるため、スタッフの説明負荷を下げられます。
このコードは強固な秘密ではなく、店頭にいる人が知りやすい合言葉です。
重要なのは不正完全防止ではなく、店頭体験の軽さと再来店動機のバランスです。

## スタッフ向け運用メモ

基本方針:
この施策は、お客様を急かすためのものではなく、本日のご来店分として次回特典をお付けする仕組みです。

お客様への案内例:
「よろしければ、本日のご来店分として、次回使える特典をお付けできます。次回は対象ドリンク1杯につき100円引きになります。店頭の2桁コードをご入力ください。」

期限を過ぎていた場合:
「前回分の特典期間は終了しておりますが、本日またチェックインしていただくと、次回は対象ドリンク1杯につき100円引きになります。」

特典使用時:
「画面に特典対象と表示されていましたら、対象ドリンク1杯につき100円引きになります。確認後に使用ボタンを押してください。」

運用上の注意:

- 全員に必ず案内しようとしなくてよい
- 混雑時は無理に説明しない
- 店頭POPで補助する
- スタッフがお客様のスマホを操作しない
- 使用済み表示が出ている場合は再使用不可
- 判断に迷う場合は管理者へ確認する

## 来店チェックイン特典情報を隠さない設計

お客様画面には、前回または最終チェックイン日、再来店特典の有効日数、期限日、現在の特典状態を表示します。

この設計の目的は、お客様が自分の状態を誤解しないようにすることです。
システム内部だけが「いつ来た扱いになっているか」を知っていると、お客様の記憶とサーバー記録がズレた時に説明しにくくなります。
Sally-Anne課題的に、システムが知っている情報をお客様本人が知っているとは限りません。
そのため、最終チェックイン日と特典対象期限を画面に明示します。

`index.html` は、Code.gs の `getCustomerState` が返す `customer_guidance` を表示するだけです。
日数判定、期限日計算、特典対象かどうかの判定はCode.gs側で行います。
これにより、`settings.benefit_valid_days` を変更しても、フロント側の計算ロジックを直さずに済みます。

表示する主な内容は次の通りです。

- 前回または本日のチェックイン状態
- 再来店特典の有効日数
- 特典対象期限
- 今日のチェックインが初回、対象ドリンク1杯につき100円引き、本日のご来店分として次回特典付与、使用済みのどれか
- 次回の特典対象期限

## お客様に見せる特典内容

お客様画面では、再来店特典カードの上部に具体的な便益を表示します。
現在の特典内容は次の通りです。

```text
次回ご来店時、対象ドリンク1杯につき100円引き
```

これはチェックイン当日に即時使用する特典ではなく、次回再来店時の特典です。
期限や対象判定は、Code.gs の `getCustomerState` が返す `state` を正本にします。
`index.html` は、特典内容の固定表示と、サーバーから返る状態表示を並べるだけです。

特典内容を変更する場合は、`index.html` の `COUPON_BENEFIT_TEXT` と、店頭POP、スタッフ説明を合わせます。
将来的には `benefit_type` や `benefit_value` を Code.gs から返し、キャンペーン別に特典内容を切り替えられるようにします。

### 収益判断式

通常粗利400円、値引き100円、値引き後粗利300円の場合、施策による利益増減は次のように考えます。

```text
施策による利益増減 = 400 × 追加販売数 - 100 × 特典使用数
```

儲かる条件は次の通りです。

```text
追加販売数 > 0.25 × 特典使用数
```

つまり、特典使用者数の25%を超える追加販売が発生すれば、粗利ベースでは黒字化します。

## v0.5 で追加したこと

v0.5では、日替わり2桁店舗コードを追加しました。

- チェックイン時のみ店舗コード入力を必須にします
- 特典使用時には店舗コードを要求しません
- 理由は、チェックイン不正はお客様にとって得ですが、特典使用不正はお客様にとって損だからです
- 2桁コードは毎日ランダム生成します
- 正解コードはフロントに置かず、Apps Script側の `settings` シートで管理します
- `settings` シートには `today_store_code` と `today_store_code_date` を保存します

- LINE通知には、LINE Messaging APIのチャネルアクセストークンとグループIDが必要です
- 未設定時はLINE通知をスキップし、`settings` シート上のコードを手動確認できます

設計思想として、フロントは入力欄とpayload送信だけを担当し、2桁コードの正解判定はCode.gs側で行います。
店舗コードはスタッフが毎回口頭で伝える秘密ではなく、店頭にいる人が知りやすい合言葉として扱えます。

### 店舗コードを2桁へ短縮した理由

店頭でのお客様入力負担を下げるため、店舗コードは2桁にしています。
このコードは強固な認証ではなく、店頭掲示またはスタッフ案内で共有する簡易的な合言葉です。
2桁化により総当たり耐性は下がりますが、特典使用には実来店と購入が必要であり、チェックイン単体では店から価値を奪えません。
不正利用が増えた場合は、`failed_attempt` イベント、短時間連続失敗の制限、時間帯別コード、QR/NFCチェックインなどを検討します。

## 店舗コードの設計思想：完全防御ではなく、管理された漏洩

2桁店舗コードは、強固な本人確認ではありません。
店頭来店をゆるく確認するための合言葉として扱います。

コードが友人間やクラス内で共有され、一部の店外チェックインが起きる可能性はあります。
この共有は完全には防ぎません。
ただし、特典使用には実際の来店と購入が必要なため、店外チェックインだけでは店から価値を奪えません。

対象ドリンク1杯につき100円引きしても粗利が正の範囲に収まる前提で設計しています。
そのため、過度な防御よりも来店動機化を優先します。
「抜け道を使った」という優越感、共犯感、裏技感が、来店促進につながる可能性があります。

これは純粋なセキュリティ設計というより、プロモーションと不正許容量を含んだゲーム設計です。
公式に共有を推奨するわけではありませんが、起こりうる共有は損益設計の中に織り込みます。

守る境界は次の通りです。

- 1つの LINE userId につき1日1回まで
- 特典使用は1つの `checkin_id` につき1回まで
- 特典額は粗利が正になる範囲に固定する
- 2桁コードは日替わりにする
- 正解コードはフロントに置かず、必ず Code.gs 側で検証する
- 機械的な総当たりは別問題として、将来的に誤入力回数制限や異常利用検知を追加する

const APPS_SCRIPT_API_URL = 'APPS_SCRIPT_API_URL';

## 同日重複防止

同じ LINE userId で同じ日に2回チェックインすると、サーバー側同日重複防止により `ALREADY_CHECKED_IN_TODAY` になります。
これは通信エラーではなく、業務上の正常ブロックです。

localStorageを消しても、スプレッドシートに今日の `checkin` 行が残っていれば、サーバー側で止まります。

## 特典使用防止

特典使用は、チェックイン行を上書きせず、`action = benefit_used` の別イベントとして追記します。
`checkin_id` により、どのチェックインに対する特典使用かを紐づけます。

同じ `customer_code` と同じ `checkin_id` の `benefit_used` 行がすでにある場合、Code.gs 側で `BENEFIT_ALREADY_USED` として止めます。

## 表示責務の整理

customerモードでは、同じ状態文言を複数箇所に出さないようにしています。

- 状態カードは「現在の結論」を表示します
- action-area は「今行う操作」を表示します
- 再来店特典カードは「履歴、期限、ルール」を表示します
- checkinNote は「チェックイン操作の補足」だけを表示します
- benefitNote は「特典使用ボタンが出ている時の注意文」だけを表示します
- 同じ文言を複数箇所に出さないよう、1情報1箇所を原則にします
- 特典使用済み時は、状態カードに「この特典は使用済みです。」を表示し、benefitNoteには同じ文言を出しません

これは、お客様の認知負荷を減らすためのUI設計です。
状態メッセージ、履歴説明、操作説明を分けることで、店頭で見せた時に「今どうすればよいか」が分かりやすくなります。

店頭操作性改善として、`action-area` は再来店特典カードより上へ配置しています。
レジ前では説明を読むことよりも、2桁コード入力欄とチェックインボタンへすぐ到達できることが重要だからです。
状態カードは「現在の結論」、`action-area` は「今行う操作」、`couponInfoCard` は「履歴、期限、ルールの確認」を担当します。
これにより、特典情報は隠さず維持しつつ、チェックイン時のスクロール量と操作負荷を減らします。
画面の自動スクロールは行わず、お客様が自然に画面を確認して操作できる状態を優先します。
LINE内ブラウザでは自動スクロールや自動focusの挙動が端末ごとに不安定になりやすいため、主操作を上に配置するだけにしています。

今日チェックインできない時は、店舗コード入力欄とチェックインボタンを非表示にします。
特典使用済み時は操作ボタンを消し、状態確認だけに寄せます。

## UI状態管理：state -> viewState -> DOM

GitHub Pages側の `index.html` では、Code.gs が返す `state` を直接DOMへ反映しません。
一度 `deriveCustomerViewState(state)` で、画面表示専用の `viewState` に翻訳します。

`viewState` は、画面表示専用の中間表現です。
業務ルールの正本は、Code.gs とスプレッドシート上のイベントログです。
`viewState` は、状態文言、表示するボタン、補足文、状態クラスをまとめます。

画面更新は次の流れにしています。

```text
Code.gs が返す state
→ deriveCustomerViewState で viewState を作る
→ applyCustomerViewState でDOMへ反映する
```

`renderCustomerState` は、クーポン説明を更新する `renderCouponInfo` と、操作UIを更新する `applyCustomerViewState` へ責務を分けています。
これにより、状態が増えてもDOM操作が散らばりにくくなります。
将来的に、状態別アイコン、多言語対応、スタンプカードUIを足しやすくするための整理です。

## 魔改造するときの見取り図

変更するときは「触る場所」と「触らない場所」を分けて考えます。
フロントは表示と操作、Code.gsは判定と保存、スプレッドシートは正本の履歴という分担を崩さないことが基本です。

| 変更したいこと | 触る場所 | 触らない場所 | 確認テスト |
| --- | --- | --- | --- |
| 特典内容を1杯につき100円から変更 | `index.html` の `COUPON_BENEFIT_TEXT`、README、店頭POP | Code.gsの日数判定 | 表示とスタッフ説明が一致するか |
| 特典有効日数を変更 | settingsの `benefit_valid_days`、管理関数 | `index.html` の日付計算 | 7日以内/8日以上で判定確認 |
| 色を変更 | `index.html` の `:root` CSS変数 | ロジック関数 | customer/dev表示確認 |
| 店舗コードを時間帯別にする | Code.gsのコード生成・検証 | `index.html` の正解判定 | 前時間帯コードが無効か |
| スタンプカード化 | `getCustomerState` のstate追加、`index.html` のviewState追加 | 既存checkin保存 | 既存特典が壊れないか |
| 多言語化 | `CUSTOMER_MESSAGES`、`customer_guidance` | `saveCheckin` | 日本語表示が壊れないか |
| 特典種別を増やす | `benefit_type` / `benefit_value` / `campaign_id` | `checkin_id`設計 | `benefit_used`紐づけ確認 |
| QR/NFC化 | `checkinFormArea`、店舗コード入力周辺 | Code.gsのサーバー検証 | フロント改造後もサーバーで検証 |
| JSONP脱却 | API通信層、バックエンド | UI状態文法 | `getCustomerState` / `saveCheckin`疎通 |
| DB移行 | Code.gsの保存・検索層 | `index.html` の表示責務 | state形式互換確認 |

### カスタマイズ文法

- 色は `:root` のCSS変数から変えます。新しい色を増やす前に、既存変数の意味を見直します。
- 来店チェックイン特典の内容は `COUPON_BENEFIT_TEXT` に置き、期限や対象判定はCode.gsのstateを正本にします。
- 状態表示は、状態カード、再来店特典カード、checkinNote、benefitNoteの責務を分けます。
- `state -> viewState -> DOM` の流れを守り、サーバー状態を直接DOMへ散らさないようにします。
- index.htmlはユーザー操作の場所なので信用しすぎません。店舗コードの正解や特典判定はCode.gs側に置きます。
- アクセストークン、groupId、店舗コードの正解はコードへ直書きしません。

## 失敗時に見る場所

- GitHub Pages 画面内のログ
- Apps Script の実行数
- `APPS_SCRIPT_API_URL` が最新の `/exec` URLか

- スプレッドシートに `checkins` タブがあるか

## 本番化前の注意

LINE userId は個人識別子に近い情報です。
本番公開前には、保存目的、保存項目、利用期間、削除対応を説明できるようにします。

MVP段階では小規模検証として扱い、デバッグUIや画面内ログは本番ユーザーに見せない形へ整理します。
